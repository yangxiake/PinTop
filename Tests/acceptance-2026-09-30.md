# PinTop 开发验收记录 · 2026-09-30

归档说明：原记录来自研究开发仓库中 `f0d014f` 时的验收文件，本次迁入公开仓库以保留早期证据。文中的 `M0c/fixture` 是当时的研究目录，公开仓库对应夹具在 `Tests/fixture`；UI 文案和默认设置均反映当时版本，不是当前操作说明。后续回归见 [测试索引](TESTING.md)。

环境：macOS 27.0 (26A428)、arm64、Xcode 27.0；SIP 开启。工程 `PinTop.xcodeproj`，本地 ad-hoc 签名，测试对象为 `M0c/fixture` 构建的两个独立 AppKit 测试应用 A/B。窗口 ID 在本次运行中分别为 22109/22108；这些数字不是跨运行稳定标识。

## 已验证

| 操作 | 观察结果 |
| --- | --- |
| `xcodebuild` Debug/Release | 构建成功；Swift 源码无编译警告。Xcode 工具链仅提示跳过未使用的 App Intents 元数据提取。 |
| A 当前活动 → pin A → 激活 B | CG 窗口列表 A 排序 0、B 排序 3；B 仍为活动应用。原窗口 ID 未变。 |
| 同一协调器 pin A，再 pin B | B 排序 0、A 排序 1；取消 A 后 B 的 pin 仍存在。 |
| 同一协调器依次 pin A/B/C | 实际 ID 顺序为 C、B、A；再次激活 A 后顺序为 A/C/B；取消 B 后 A/C 仍保留，最终全部取消通过。 |
| 同一应用双窗口 | 两窗分别钉住；取消第一窗后第二窗的辅助成员仍能读回，未误取消。 |
| 用户最小化并还原测试窗口 | 最小化后暂停辅助层而保留 pin；还原后重新显示且成员读回通过。 |
| 正常单项取消 | 添加的辅助成员被撤销，helper 解除守护；下一次置顶可正常进行。 |
| 主进程 `SIGKILL` | 独立恢复进程写出 `PASS`，撤销辅助成员并销毁自建 Space。 |
| 主进程与 helper 均 `SIGKILL` | 下次启动扫描经过进程启动身份、系统启动时间、窗口 owner 和成员关系检查后写出 `PASS startup`。 |
| 本地应用包 | `build/PinTop.app` 使用 Xcode 工程构建，ad-hoc 签名验证通过，能够启动为菜单栏进程。 |
| 独立应用辅助功能授权 | 只重置 `local.pintop.app` 的辅助功能记录后，在“设备控制和数据访问”中为最终 `build/PinTop.app` 重新开启；系统设置中 PinTop 开关为开启。LaunchServices 独立启动自检返回 `AX_TRUSTED=true NEEDLE_TAP=available`，控制窗口刷新后显示“辅助功能：已授权”。当前构建的 CDHash 为 `3f0db5372e30d395d02810ec760f14f52e17ee58`。 |
| 单实例与单一构建路径 | 用户报告电脑上出现多份 PinTop 时，实际检查到四个主进程，分别来自项目 `build`、项目 DerivedData Debug/Release 及 Xcode 全局 DerivedData。关闭旧进程后，Xcode Debug 和构建脚本均改为输出项目 `build/PinTop.app`；三个旧生成包注销并移至废纸篓。`xcodebuild -showBuildSettings` 显示 Debug 的 `CONFIGURATION_BUILD_DIR` 指向项目 `build`，工作区内搜索仅剩一份 `PinTop.app`，当前仅一份主进程运行。用户级非阻塞 `flock` 仍保留。 |
| 控制窗口与设置 | 首启控制窗口的实际画面显示窗口图标、名称、钉住/取消置顶按钮及角标、Dock、登录启动开关。列表可滚动，顶部有“全部取消”；钉住成功后控制窗口收起。通过界面关闭和恢复角标，持久值一致。登录启动项在本次清理后关闭，`sfltool dumpbtm` 显示 PinTop 为 `disabled`；Dock 图标当前关闭。 |
| 角标取消 | 控制窗口钉住 ChatGPT 后出现取消角标和恢复 helper；图形自动化点击角标时目标窗口从接口中消失、调用超时，但后续 `disarmed` 文件出现、helper 退出。按清理结果确认已取消，视觉过渡未验收。 |
| 当前独立应用控制窗口 pin A | 当前构建通过控制窗口的“钉住”按钮操作临时窗口 A。A 的原窗口 ID 保持 22937，窗口层级为 0；激活未钉住的 B 后，B 成为活动应用，而 A 的 CG 顺序为 2、B 为 13，A 仍在 B 之上。 |
| 当前独立应用输入与取消 | 钉住期间，A 的原生文本框收到 `PinTop QA`，夹具状态记录在原窗口 ID 22937 下。点击角标取消后，恢复 helper 退出，恢复日志产生 `disarmed`；当前仅剩一个 PinTop 主进程。自动化调用因角标窗口消失而超时，取消结论依据后续状态确认。 |
| 针模式可见反馈与实际选择 | 用户用实体鼠标确认悬停边框与图钉提示可见；意外点击后，恢复日志记录 Xcode 原窗口 ID 22206 被钉住，管理窗口显示“取消置顶”，点击后 `disarmed` 出现、helper 退出。再次误点 ChatGPT 后也通过管理窗口取消。最终构建将跟随鼠标的提示改为屏幕顶部固定提示，图形界面检查可见“📌 点击窗口以钉住 · Esc 退出”和“取消选择”按钮；点击“取消选择”后提示消失、无新增 pin。实体键盘 Esc 尚未实测。 |
| 图钉角标取消 | 新角标改为强调色背景和白色图钉；对临时 A 的界面截图可见图钉，点击后 `disarmed` 出现，helper 退出。 |
| 窗口内置顶标记与无感交互 | 用户指出旧版钉住后弹回 PinTop，且取消入口不明显。当前构建用临时 A 验证：从列表钉住后管理窗口收起、A 保持活动及键盘焦点，PinTop 的可见窗口只剩位于目标标题区域的“已置顶 · 取消”按钮；按钮截图可辨认图钉与文字。点击按钮后 `disarmed` 出现、helper 退出，管理窗口未弹回。当前 Dock 图标开关关闭、登录启动关闭，应用以菜单栏方式运行。 |
| 通用角标层级修复 | 用户复测 Codex 窗口时看不到角标。排查发现旧角标虽已创建，却排在已钉原窗口后方。修复后每个角标加入其目标窗口的辅助 Space，并验证角标在 CG 窗口列表中排在原窗口之前；失败则自动撤销该次置顶。独立临时窗口 A：原窗口 ID 23652、角标 ID 23683，排序分别为 1、0；Codex/ChatGPT：原窗口 ID 22372、角标 ID 23693，排序分别为 1、0。两次整屏截图都能看到蓝色“已置顶 · 取消”覆盖在相应窗口右上角；通过角标点击取消后各自恢复记录出现 `disarmed`。这是按窗口对应的 Space 工作，不含针对 Codex 的分支。窗口 ID 仅对应本次运行。 |
| 单次空闲资源快照 | 应用包约 836 KiB；启动约 5 秒时 RSS 52,864 KiB、CPU 0.0%。RSS 超过文档的 50 MB 目标，仍需进一步测量和优化。 |

这些结果验证内核与恢复路径，不等于完整产品验收。CG 顺序与焦点来自测试夹具和窗口元数据；没有把菜单兼容记为通过。

## 待人工 UI 回归

- 首次授权、拒绝/撤销/重授的完整用户流程，以及实体键盘 `Esc` 的针模式行为仍需回归。用户两次想测 Esc 时均意外先点击了普通窗口，因此没有把 Esc 写为通过。系统设置中的旧 PinTop 行虽显示开启，却让独立应用返回 `AX_TRUSTED=false`；按 bundle ID 定向重置并重新开启当前构建后变为 `true`。本地 ad-hoc 重新构建会产生新 CDHash，需要重新授权对应构建。
- 限时针模式诊断运行了 30 秒，图形自动化在临时窗口 A 上发出了两次点击及一次 `Esc`，窗口 A 收到了点击；针模式的事件计数为 `0`，输出 `TIMEOUT EVENTS=0`。这表明该自动化输入未经过 PinTop 的 CGEventTap，因此不能用这次诊断判定真实鼠标交互通过或失败。
- 角标位置与点击已在临时窗口 A 和 Codex/ChatGPT 的当前布局通过；移动/缩放跟随及多屏位置仍需回归。应用原生编辑、拖拽、右键、中文输入法仍待回归。
- 两个普通桌面、Mission Control、全屏与多显示器；锁屏/安全 UI。
- 同应用多窗口与三窗口已完成夹具排序回归；真实鼠标点击顺序、应用自身窗口重建仍待 UI 回归。
- 菜单和候选窗遮挡属于已知未通过项。

图形自动化接口可查看控制窗口、固定提示、角标、测试夹具和系统设置；其模拟点击未经过 PinTop 的 CGEventTap。Xcode 调试界面仍未通过该接口完成回归；没有申请屏幕录制权限。
